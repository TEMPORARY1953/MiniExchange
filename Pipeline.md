# Пайплайн работы MiniExchange

**Существующий Matching Engine**

`OrderBook::add_order()` принимает `Order{id, side, price, quantity}`
и возвращает сделки в порядке исполнения. Один стакан обслуживает один инструмент.

1. **Проверка.** ID, цена и количество должны быть положительными, сторона —
   допустимой, ID — уникальным за всё время жизни стакана. Ошибка вызывает
   `std::invalid_argument` без изменения стакана и резервирования ID.
2. **Выбор встречной заявки.** Для `BUY` выбирается самая дешёвая продажа,
   для `SELL` — самая дорогая покупка. Внутри цены действует FIFO по порядку
   вызовов `add_order()`, независимо от ID.
3. **Проверка цены.** Покупка исполняется, если её лимит не ниже цены продажи;
   продажа — если её лимит не выше цены покупки. Если лучшая цена не подходит,
   сопоставление заканчивается.
4. **Сделка.** Количество равно `min(incoming.quantity, resting.quantity)`,
   цена берётся у заявки, уже стоящей в стакане. Оба остатка уменьшаются.
5. **Обновление.** Исполненная встречная заявка удаляется, пустой уровень тоже.
   Частично исполненная сохраняет место в очереди. Пока есть входящий остаток,
   поиск повторяется.
6. **Остаток.** Неисполненная часть входящей заявки добавляется в конец очереди
   по её собственной лимитной цене. ID принятой заявки остаётся занятым даже
   после полного исполнения.
7. **Вывод результата.** Метод возвращает сделки в порядке исполнения.
   Консольный пример в `app/main.cpp` выводит сделки и снимки стакана.

Ценовые уровни хранятся в `std::map`, очереди на уровнях — в `std::deque`.
Метод `orders(Side)` возвращает копию оставшихся заявок по цене и FIFO.

**Пример исполнения заявок**

До поступления покупки в стакане стоят продажи:

| Порядок поступления | ID | Цена | Количество |
| ---: | ---: | ---: | ---: |
| 1 | 1 | 100 | 5 |
| 2 | 2 | 100 | 4 |
| 3 | 3 | 101 | 6 |

Поступает `BUY #4`, цена 101, количество 12:

1. Исполняются 5 единиц против #1 по цене 100; остаток покупки — 7.
2. Исполняются 4 единицы против #2 по цене 100; остаток покупки — 3.
3. Исполняются 3 единицы против #3 по цене 101; покупка исполнена полностью.

В стакане остаётся `SELL #3`, цена 101, количество 3.

**Взаимодействие компонентов конечной системы**

Этот поток предполагается для завершённого симулятора; сейчас реализовано
только описанное выше ядро с лимитными заявками.

1. **Отправка заявки.** Пользователь из браузерного терминала или торговый бот
   передаёт заявку BUY/SELL в backend.
2. **Проверка.** Backend проверяет параметры и доступные виртуальные средства
   участника, резервирует средства для принятой заявки.
3. **Matching Engine.** Backend передаёт заявку C++-движку, который выбирает
   встречные заявки по цене и FIFO.
4. **Исполнение.** Движок выполняет полное или частичное сопоставление,
   возвращает сделки и обновляет остатки заявок в стакане.
5. **Обновление данных.** Backend пересчитывает балансы и резервы по результатам
   сделок, обновляет историю и получает актуальное состояние стакана.
6. **Отображение результатов.** Терминал показывает стакан, сделки и график цены;
   боты получают данные для следующих решений и сравнения результатов стратегий.

При отмене backend передаёт команду движку и освобождает резерв
неисполненной части после подтверждения отмены.
